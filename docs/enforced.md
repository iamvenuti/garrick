# What is enforced, and what is asked

Some of Garrick's protections are code: a script that refuses, whatever the assistant intends. The rest are rules the assistant is asked to follow, and they hold only as well as it follows them. This page says which is which, so you can judge each one for what it is.

## The table

Garrick's own commits (the status page's actions, the scaffold tool and the scheduled jobs) run git without the caller's repository variables (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and git settings passed in the environment), and refuse to commit in a zone when the hook git would run is not Garrick's wall check, wherever that hook is configured or the repository is.

## Allow once

A refusal that is a false alarm can be let through for one finding of one file, and for as long as the file stays as it is. The user does it; an assistant never does. Two places write one: `check.py allow`, typed in a terminal, and a button on the Context queue in the Mac app. The allowance is kept in `System/walls-allowed.json`, in the workspace's own repository, so the history says what was let through and when.

```json
{
  "version": 1,
  "allowed": [
    {
      "path": "Zones/Work/Acme/Acme.md",
      "id": "3f9a1c2b7d",
      "blob": "e69de29bb2d1d6434b8b29ae775ad8c2e48c5391",
      "rule": "name",
      "date": "2026-11-10",
      "by": "terminal"
    }
  ]
}
```

- `path`: the file's path from the workspace root, with forward slashes.
- `id`: the first ten hex characters of SHA-1 over `path`, `rule` and the finding's matched text, joined by a NUL. The matched text is never stored, so the ledger names no zone content and no person.
- `blob`: git's blob id of the file as allowed. The hook reads it from the index (`git ls-files -s`) and hashes nothing; a full run hashes only the files that have a finding. An edit changes the blob, so the finding comes back.
- `rule`: the kind of the finding, one of `link`, `wording`, `path` or `unlabelled`. A finding that cannot be read, or a file waiting in an inbox, is never allowed.
- `date`: the day it was written. `by`: `terminal` (typed in a terminal) or `page` (the queue's button).

An entry covers a finding only when `path`, `id` and `blob` all match, so an allowance for one finding does not cover another in the same file. A file is cleared only when every finding it has is allowed, counting a second finding about a meeting the report leaves out as already named: allowing the first of two never lets the second through, and `check.py allow <path>` lists them all. The check reads the ledger as the workspace's own repository holds it at `HEAD`, once a run: a file written by hand or edited and not committed allows nothing, and a workspace with no repository has no allowances. A ledger that is missing, unreadable or of another `version` holds no allowance, and every refusal stands as before. `allow_read` and `allow_add` in `System/tools/garrick_lib.py` read and write the file; `check.py` drops an allowed refusal (`drop_allowed`) and writes one (`allow_page`), and `page_action.py` has the verb `walls-unallow`, which takes an entry away, and the two verbs of the queue's wall question, described below.

### The Context queue's button

A wall finding in the Context queue is asked in plain words, and no answer is recommended until you have seen what matched. In the Mac app the page runs the wall check for the file when the question opens, so the question names the file. *Show me both texts* reads the words the two files share, and a few words around them in each, into the dialog. They are never written to disk, to the page's data, to a log or to the operations record, and they are dropped when the dialog closes. Only after that does *The words are mine, keep them* show. It writes the same entry `check.py allow` writes, with `by` set to `page`, for one finding of one file, and commits `System/walls-allowed.json` alone in the workspace's own repository. The request carries the file as the dialog showed it: if the file has changed since, nothing is written. It covers a match of wording, the one kind whose shared words the dialog can show. *Remove* under Settings, Walls, takes an entry away, as before.

A browser has no bridge to the app, so it shows neither the look nor the button, and *Take it out* stays as it was: your assistant removes the material and shows you the change. The ask box and a session are refused for both the look and the allowance, and the command line has no verb for either. No skill, document or Ask tool names them. The page is a second writer because you pressed the button after seeing both texts. A process that sends the page's request the way the app does is taken for the page, as it is for every page action; the guard is against honest mistakes, as the rest of the wall check is.

## The wall check's known gaps

The check is for an honest writer's mistakes, as [the threat model](principles.md#the-threat-model) says. It does not catch everything. These are the gaps an honest writer could hit, by kind, and one line each.

**Links**

- A link to a file that does not exist, or that Obsidian would not open, is not followed.
- A path in plain prose, outside a code span, is not read, except a path that names a Meetings page by its whole path or by two names or more.
- A name with shell separators or more than eight words, after a command, in a layout folder (`Threads/`, `Sources/`, `Deliverables/`, `Notes/`) written without its project, is not refused. Quote the name or write the project.

**Names**

- No name is matched. A client's name typed into a file of another zone is not caught, in any spelling: only links, embeds, paths and copied files are.

**Wording**

- A clean paraphrase passes, and so does wording moved rather than copied; only git history shows where it came from.
- A document copied by hand into `Sources/`, and an attachment that was edited, pass. An exact copy of a mail attachment is caught by a separate byte comparison.
- Word, PowerPoint and PDF contents are not read.
- Stock wording passes: a run of words that files of three zones or more hold, or more than five files (`wall-common-files`), is not read as a quote. A sentence lifted from one meeting is still refused, and a missing count makes nothing stock.

**Paths**

- A path to a folder, with or without its slash, ends at the folder.
- A path built from a shell variable is read as the variable's text, not the path it makes.
- A Resume here or checkpoint path that lands in another zone, and any change made in a repository with no hook, are reported only by the full check (#340). The root repository has no hook by default.

**Merges**

- A fast-forward, a rebase and a cherry-pick bring commits in with no hook that can refuse them. The post hooks run `check.py --changed` over the files those commits changed, read only, and print what they find: the commits are already in, so they refuse nothing, undo nothing and write nothing. `post-merge` covers a merge or a fast-forward (`ORIG_HEAD..HEAD`) and says nothing for `git merge --squash`, which commits nothing and leaves its files to the pre-commit check. `post-rewrite` runs after a rebase, including `git pull --rebase`, and covers the rewritten commits and what the rebase brought in from upstream, and after `git commit --amend`, and covers the amended commit. The report names how to undo it without running it: `git reset --hard ORIG_HEAD` after a merge or a rebase, `git reset --soft HEAD@{1}` after an amend, which sets no `ORIG_HEAD`. A cherry-pick runs neither hook.
- A merge hook that is the user's own is never replaced: `check.py` warns and says the line to add to it (`--staged --walls-only` for `pre-merge-commit`, `--changed` for the post hooks) and the words in a comment that tell the check the hook runs it.

**By design**

The check does not read a form that needs deliberate disguise to pass: a look-alike letter or slash, invisible characters, an escaped or encoded name, a path assembled from parts, a name split across lines. These are not gaps and not vulnerabilities; see [SECURITY.md](../SECURITY.md#what-is-not-a-vulnerability). A clean result means the implemented checks found nothing, not that nothing crossed. [What the check covers](principles.md#what-the-check-covers) sets out the four things it does read.
